# 佛教大藏經 /tripitaka

`/scripture-canon` → 佛教 → **佛教大藏經**。與基督教區的八個子工具、希臘羅馬的
《希臘羅馬大藏經》平行並列。

### DK 的書目後設資料：84000（`scripts/tripitaka_derge_titles.py`）

`tripitaka_derge.py` 從 TEI 正文抽藏文題名（1,075／1,124），梵文題名、英譯題名與
譯者另從 **84000 的 Linked Open Data** 補（GitHub `84000/data-rdf`，**CC0**，
1,254 個 RDF 涵蓋 Toh 2–4458，甘珠爾加丹珠爾）。用 tarball 一次抓，不要逐檔抓 1,254 次。

補完：藏文題名 **99.4%**、梵文題名 77.8%、英譯題名 98.5%、譯者 41.9%。

| 欄位 | 來源 |
|---|---|
| `title_bo` | 本站從 TEI 正文抽的**全名** |
| `title_bo_short` | 84000 的**通行略稱**（兩者並存，不互相覆蓋） |
| `title_sa` `title_en` | 84000 |
| `translator_en` | 84000 的**現代英譯者**（Gareth Sparham…），**不是**九世紀的藏譯譯師。別填進 `byline`／`translator` |
| `title_zh` `zh_parallels` | **東北目錄**（`tripitaka_derge_zh.py`），見下 |

#### 🚨 這一步踩到的四個坑

1. **`title_sa` 有 21% 是假的。** 84000 在「這部經沒有梵文題名」時，`WAITOH`
   那一格塞的是英譯或 `[no Sanskrit title]`。照收的話 238 筆的梵文題名會是英文，
   而頁面顯示「梵文題名：The Sūtra of Vasiṣṭha」**看起來完全正常**。
   判準：梵文轉寫不會出現英文虛詞（the／of／on／to…）。修掉後 1,119 → 874。
2. **梵文題名裡有軟連字符**（U+00AD）。`Saddharma­puṇḍarīka` 看起來正常，
   但站上搜「Saddharmapuṇḍarīka」永遠查不到。要清掉 U+00AD／U+200B／U+FEFF。
3. **RDF 的四個 `skos:prefLabel` 都沒有 `xml:lang`**，只能靠掛在哪個
   `rdf:Description` 分辨：`WAITOH`＝梵＋英、`WATTOH`＝藏、`WAETOH`＝英＋譯者。
4. **兩邊的藏文題名比對不能用字串相等。** 本站抽的是正文全名，84000 給的是
   通行略稱（`ཤེར་ཕྱིན` 是 `ཤེས་རབ་ཀྱི་ཕ་རོལ་ཏུ་ཕྱིན་པ` 的標準縮寫），
   本站保留敬語前綴而 84000 多半省略。直接比會得到「879 筆不一致」，
   讓人以為切錯了七成八的經。改用**最長共同片段**（與縮寫慣例無關）：
   92.9% 有 ≥8 字母的共同片段、6.3% 有 5–7，合計 **99.2% 確認是同一部**。
   剩下 9 筆逐筆看，挖出本站的真實缺陷——**4 筆題名只抽到敬語前綴「聖」本身**
   （Toh 548／796／894／1035），正題名沒抓到。那幾筆改採 84000 的。

### DK 的漢譯對照：東北目錄（`scripts/tripitaka_derge_zh.py`）

甘珠爾是藏譯，**沒有「漢文書名」這種東西**。能填的只有「漢譯對照本」——
同一部印度原典另外譯成漢文的那一部經。這個關係不能猜，只能抄目錄。

來源＝**東北大學 touda.tohoku.ac.jp 的西藏大藏經資料庫**，即 1934 年宇井伯壽等編
《西藏大藏經總目錄》（Toh 編號的出處）的官方數位化。每筆詳目的「内容構成」表
列出漢譯對照本並附 **SAT No.＝大正藏經號**。爬法：`canon/{id}`，
id ＝ `1501001` ＋ 7 位流水號，甘珠爾是 1–1109。

| | |
|---|---|
| 涵蓋 | **447／1,124（39.8%）** 有漢譯對照（單一 229、多部 218） |
| 無漢譯對照 | 661（多為密續，本來就沒漢譯） |
| 東北目錄無此條 | 14（Esukhia TEI 細分出的後綴本 `539a–f` 等，留空不套母條） |
| `title_zh` | 主對照本的**繁體**書名 | 
| `zh_parallels` | `[{id, t, title}]` 全部對照本；`checked:false` ＝ 待判讀 |

**做法的核心：只取 SAT 經號，書名回我們自己的 CBETA 目錄拿。**

#### 🚨 這一步踩到的六個坑

1. **絕對不要抄東北大那一欄的漢文書名。** 它是日本新字體，而且有系統性錯字。
   光 Toh 1 一部就四處（`膳意事`→隨意事、`設`→說、`毘奈那`→毘奈耶、`薬`→藥），
   另見 `大賓積經`（寶→賓）、`大般若波羅蜜多罷`（經→罷）、`增ー阿含親`、
   `觀世昔菩薩`（音→昔）、`無凝`（礙→凝）、`佛說大般泥恆經`（洹→恆）。
   照抄會得到一個長得完全像漢文書名、其實是日文加錯字的字串，**肉眼看不出來**。
   取經號回查 CBETA 目錄，這些全部自動校正。

2. **一格可以掛多個 SAT，`.search()` 只會拿到第一個。** 而且多個書名是
   **直接黏在一起、沒有分隔符**的（Toh 44：`大方廣佛華厳経［八十華厳］（…）普賢菩薩行願讃`
   後接兩個連結）。用 `.search()` 的話「多部對照」從 **218 掉到 1**，
   Toh 176 從三部縮成一部，而目錄照樣有值。要 `finditer`。

3. **主對照本不能用「經號最小」挑。** Toh 120（大般涅槃經）對到
   T0037／T0375／T0376，取最小號會挑到《緣本致經》——一部毫不相干的小經。
   正解：東北大一格裡只寫**一個代表性書名**，那就是它認的主對照本；
   用 `jp2t` 抹平字形後拿它去比，比中的那一部當主。

4. **CBETA 的分卷有兩種，不能一律取第一個。**
   (a) 真的是不同的經共用一個大正藏號（T1005A《大寶廣博樓閣善住祕密陀羅尼經》
   vs T1005B《寶樓閣經梵字真言》、T0974A–F）→ 拿書名比對挑。
   (b) 只是按檔案卷段切開、書名一樣（T0220a–p）→ **把卷段括號拿掉回傳本名**。
   不分的話，Toh 8／9／10／12… 十二部不同的般若經會全部顯示成
   「大般若波羅蜜多經(第1卷-第200卷)」，而 Toh 10 其實是第三會。
   另外密教部的分卷用**大寫** A／B，般若部用**小寫** a–p，只認小寫會漏 7 個經號。

5. **對帳閘只能用在「一格一個 SAT」。** 一格多個 SAT 時它只寫一個代表性書名，
   逐名比對必然失敗——實測 50% 門檻擋下 37 筆，其中 **36 筆是對的**。
   而且對不上也不代表錯：多半是「藏文對到漢譯某部經**當中的一品**」
   （Toh 289「頻鞞娑邏王迎佛經」＝《中阿含經》第 62 經，所以經號給母經、
   書名寫品名）。所以閘**只標記不丟棄**，確定錯的才進 `UPSTREAM_WRONG`。

6. **東北大自己會標錯經號。** Toh 119 書名寫「大般涅槃経（巻第一…巻第四十）」，
   SAT 卻掛 **0874**＝《金剛頂一切如來真實攝大乘現證大教王經》，一部密續
   （多半 0374 打成 0874）。照收的話涅槃經底下會冒出一部金剛頂經，
   頁面上完全看不出異常。正確經號無從由該資料推定，**留空不臆造**。

#### 試過而不能用的四條路（別再試一次）

* **84000 `data-rdf`** — 1,254 個 RDF 檔，**零個漢字**，只有藏／梵／英。
* **rKTs** — 藏文本位（強項是各版甘珠爾的版本異同），頁面裡沒有 Taishō／南條編號。
* **SuttaCentral parallels** — 德格↔大正藏只有 **14 組**，落在我們目錄內 13 組。
* **Lancaster《高麗大藏經解題目錄》**（acmuller.net，有 Tōhoku 索引）— 全藏只標了
  391 個 Toh，甘珠爾段 **313 個（27.8%）**，是隨手註的交叉參照不是系統性對照表。
  站台只走 http，https 會 ECONNREFUSED。

#### 兩個一般性的教訓

* **`--catalog-only` 會洗掉別的腳本併進來的欄位。** `tripitaka_derge.py`
  用固定欄位白名單重出目錄，`title_sa`／`title_en`／`translator_en`／
  `title_zh`／`zh_parallels` 都不在裡面，重跑一次就沒了，而部數照樣 1,124、
  結構照樣完整。已改成 `_merge_kept()`：非本次解析產出的欄位一律原樣帶回。
* **快取寫 Drive 會慢五倍。** 同樣 1,140 個 46KB 檔，寫 `G:` 只跑 8 頁／分
  （請求本身 0.3–1 秒，其餘全耗在 DriveFS 逐檔同步），寫 `C:/tmp` 是 28 頁／分。
  照 repo-hygiene 判準這本來就是快取。

#### 🚨 接上網站時踩到的五個坑

1. **`isValidWorkId` 只認 T 與 N，卍續藏那 1,230 部全部打不開。** 這是既有的洞，
   加 DK 時才發現：`/api/tripitaka/work?id=X0001` 一律回 400，而首頁照樣列得出
   1,230 部與字數，**只有點進去才壞**。這個函式同時是路徑注入的唯一防線，
   加代號一定要連它一起改並補測試（`test/tripitaka-work-id.spec.ts`）。

2. **reader 的預設欄寫死 `'lzh'`。** 甘珠爾只有 `bo` 一欄，`cols` 會算成空陣列，
   於是整部經一個字都不顯示——而頁框、段號、側欄全都正常出得來，
   看起來像「這部經是空的」而不是「欄位選錯了」。改成「留下有資料的，
   一個都不剩就取第一個」。

3. **甘珠爾沒有「卷」，不能靠 `juan` 分頁。** 它的段只有 `vol`／`folio`／`line`，
   `juans` 會是空陣列、`juan` 為 null，於是**整部一次送出**：Toh 8 有 65,897 行、
   1,290 萬字，瀏覽器直接卡死，而回應是 200、資料也都對。
   改用 `dkPages()`：先按函切，函內再按 1,200 行切，頁名用起訖葉碼。
   單函最多 5,737 行（Toh 8 第 24 函），所以函內一定要再切。

4. **`translator_en` 是 84000 的現代英譯者，不是藏譯譯師。** 值長這樣：
   Gareth Sparham、Gyurme Dorje、Andreas Doctor。填進 `byline`／`translator`
   的話，頁面會在一部九世紀藏譯經旁邊寫「譯者：Gareth Sparham」，
   完全看不出不對。那兩欄對 DK 留空，英譯者另標「84000 英譯」。

5. **正文 LRU 的上限要按位元組算，不能按筆數算。** 原本是「最多 12 筆」，
   在漢文是安全的（一部幾 MB），但甘珠爾一部到 47 MB JSONL／65,897 段，
   解析成 JS 物件單部上看 150 MB，12 筆能吃掉 1–2 GB。改成 256 MB 上限。

## 🚨 段怎麼切、怎麼編號（使用者定調，別再改）

**漢文佛典沒有聖經那樣的章節制。**章節是 13 世紀 Langton、16 世紀 Estienne
硬加的內容邏輯切分，全教會統一採用；佛典從來沒有過這樣一次性的統一編碼工程。

本站的定調：

```
段的鍵 ＝ 該段第一行的大正藏頁欄行     T09n0262_p0008a13
段的邊界 ＝ CBETA 新式標點本的 <p>／<lg>（編輯判斷，非原典自帶，凡例須註明）
```

行號是版面座標不是文本單位（換一個藏本就對不上），但它是學界引用漢文佛典的
**唯一標準**，所以拿來當鍵與引用式都對，拿來當跨語言對齊鍵則錯（梵藏本沒有
大正藏頁碼）。

## 🚨 踩過的坑（每一個都是「看起來成功的失敗」）

全部由 `scripts/tests/test_tripitaka_*.py` 鎖住。動這批程式前先讀這一節。

1. **`<cb:div type="equiv-notes">` 在 cb: 命名空間下。**
   用 `root.iter("{TEI}div")` 找會**靜默回 0 筆**、不報錯。要比對 local name。
   雜阿含的 917 條巴利對應就是這樣整批消失過。

2. **南傳的經號是「冊內序號」。**
   `N01n0001` 與 `N02n0001` 是兩部不同的書。分部只能按**冊號**，
   作品 id 也必須帶冊號（`N09n0001`）。按經號分部會把整套書分錯。

3. **`sa-2.180` 是別譯雜阿含第 180 經，不是雜阿含 2.180。**
   正規式切前綴會把它併進 `sa`，再被「取小數點前」的退路默默對到
   雜阿含第 2 經 —— 而且**會被統計成命中**。必須用已知集號做最長前綴比對。

4. **四部阿含的經號位置各不相同。** 硬套一種會整批對錯：

   | | 經號在哪 | SC 編號式 |
   |---|---|---|
   | T0001 長阿含 | 標題「（一）」 | `da1`–`da30` |
   | T0026 中阿含 | 標題「（二二二）」 | `ma1`–`ma222` |
   | T0099 雜阿含 | 標題「（一二六七）」＝大正藏經號。🚨**不是** `cb:mulu n`（n 只有 139/1,349 相符，差 2–7 號；2026-10-01 前認 n，九成巴利對照掛錯經，以 SA262 闡陀↔SN22.90 等內容驗證後改正） | `sa1267` |
   | T0100 別譯雜 | 標題，且 div type 是 `other` 不是 `jing` | `sa-2.180` |
   | T0125 增壹阿含 | n 是**品內**序號 | `ea32.2`＝品32經2 |

5. **大正藏標題的漢數字是逐位排列**（二二二＝222、三〇＝30），不是十百進位。
   兩種都要吃。

6. **`t213.4` 的品號不可丟。** 只取 213 會把法句經群（T210／T212／T213 ↔ 巴利
   Dhammapada ↔ 梵文 Udānavarga ↔ 藏譯甘珠爾，本藏最完整的四語對照）
   四千多筆逐品對照全塌成「整部」。段落級命中率會從 87% 掉到 30%。

7. **`<cb:tt>` 在正文中出現時，三種語言會串成一團。**
   「長阿含經Dīrgha-āgamaDīgha-nikāya」。正文只取 `zh-Hant` 那一支。

8. **目錄部的經錄把書目寫成 `<item><title>`，底下沒有 `<p>`。**
   只收 `<p>/<lg>` 會讓整批目錄部解析成 0 段或十幾個字。`cb:jhead` 同理。

9. **對不到段落的對照不要收。**
   律典的 uid 是逐條學處（`lzh-mi-bi-vb-pc12`），對不到段落時全部塌成
   「十誦律 ↔ 巴利律藏」，同一句話重複三萬七千次。那不是對照，是噪音。
   捨棄的 143,763 筆在 `--audit` 輸出中明列，不靜默丟。

10. **原文與漢文不可左右並排。**
    原文那一側是「一整部經」，漢文這一側只是該經的起首段。並排會讓讀者
    以為第 n 段漢文正對第 n 段巴利 —— 漢巴兩本的段落數本來就不一樣。
    故做成可展開區塊，並在區塊內明寫「同源異流的兩個本子，段落非一一對應」。
    **例外（2026-09-30 使用者要求）：「逐經並排」模式**——以目錄節點（一經）為單位，
    左漢文整經、右原文整經，粒度停在經號（漢巴兩邊都有共識的單位）。成立條件：
    每個節點恰好一段掛原文（五部阿含實測 29／193／955／314／200 經、零例外），
    不成立時 `sutraGroups` 回 null、退回逐段檢視。經以下仍不逐句對，頁面上明寫。
    學界沒有跨語言的「節」：巴利有 PTS 頁碼與 SuttaCentral segment id、漢文有大正藏
    頁欄行、梵本用校訂本頁碼或頌號、藏文用德格葉碼，四套各自為政，互不對應。

11. **`t2917A`／`t2917B` 是同號兩本。** 經號有字母後綴，`int()` 會直接炸。

12. **法句經那類在 SuttaCentral 是區間檔名**（`dhp1-20`、`dhp100-115`）。
    單經 uid（`dhp21`）直接查索引會漏掉 1,640 筆，要另建區間索引。

13. **梵漢照品序對齊是本專案最危險的一招。**
    法華梵本 27 品、羅什漢譯 28 品（提婆達多品在梵本併入見寶塔品），照順序對
    會讓第 12 品以後全體位移一格，**而頁面看起來完全正常**。
    `tripitaka_sanskrit.py` 的規矩：品數不合一律拒絕逐品對齊、退回整部層級並
    在 `--audit` 明列；要逐品對就得手寫 `chapter_map`。絕不用「長度差不多就湊」。

14. **GRETIL 的頌號標在偈的末行**（`d e f // MMK_1.2 //`）。
    逐行判品會讓每一品的首半偈被算進上一品 —— 要以偈頌組（`<lg>`）為單位取標記。

15. **不要自編看起來像引用式的行號。** 一度把梵文行號寫成 `MMK_1:3`（自編序號），
    那長得像頌號卻不是。現在只用原書真有的頌號，抓不到就留空。

16. **CBETA 有時不給 div 的 `type`。** 道行般若 T0224 只有第一品標了 `pin`，
    其餘 29 品是空字串 —— 只認 `type=='pin'` 會把整部書判成「無品層」。

17. **法華的梵漢差異有兩處，不是一處。** 我第一版只處理了「提婆達多品併入
    見寶塔品」那一處，寫成「梵 12 起加一」—— 結果尾段**四個品全配錯**
    （陀羅尼、妙莊嚴王、普賢、囑累），而頁面完全正常。
    真相是羅什另把**囑累品移到第 22**、陀羅尼排到第 26；梵藏本則陀羅尼在 21、
    囑累在最末 27。正確對照見 `tripitaka_sanskrit.REGISTRY` 的 T0262 那一筆
    （藏譯 Toh 113 章序與梵本一致，`tripitaka_tibetan` 直接取用同一張表，
    不各抄一份）。教訓：**手寫的對照表本身也要驗**，閘只擋得住數量不符，
    擋不住數量相同但次序不同。

18. **84000 TMX 的「This concludes … the Nth chapter」是章尾不是章首。**
    當成章首會讓章數翻倍且內容錯位。

19. **漢譯南傳的五尼柯耶編號方式互不相同**，且相應部有三個疊在一起的陷阱：
    ① 相應號**每冊重新編**（N17 從「第八 聚落主相應」起，跨篇又跳回
       「第三 念處相應」）→ 不能讀標題序數，要跨六冊照文件順序連號。
    ② N14 把相應與其下的品**放在同一深度**，父子鏈是斷的 → 不能用
       parent 往上找，改用「文件順序上最近的前一個相應」。
    ③ 判別相應要看**標題結尾是不是「相應」**，看深度會把「食品」也算成相應。
    任一條沒處理好，1,691 經整批位移而頁面看不出來。
    閘：長部必須恰好 34 經、中部 152 經、相應部 56 相應 —— 都是巴利藏的定數，
    對不上就整個尼柯耶不掛。

20. **PostgREST 的三個寫入坑**（灌 tripitaka_parallels 時一次踩齊）：
    - 唯一索引若寫成 `coalesce(seg_uid,'')` 是**運算式索引**，`on_conflict`
      認不得 → 42P10。改成一般欄位索引，整部層級的列存空字串而非 NULL。
    - 同批次出現重複的唯一鍵 → 21000「cannot affect row a second time」。
      同一漢文段可能從兩個平行組收到同一筆對應，**推之前要去重**
      （23,321 筆去重後剩 10,168）。
    - 回填 `parallel_langs` 不可用 upsert：那是 INSERT…ON CONFLICT，
      只給三個欄位會撞 NOT NULL → 409。要用 `UPDATE…FROM`。

21. **🚨 CBETA 的字母後綴兩種大小寫都用**（`T0128a`／`T0128b` 小寫，
    `T1670B`／`T2917A` 大寫），不能一律轉大寫，也不能照 SuttaCentral uid 的
    小寫直接用。而 **Windows 檔名不分大小寫** —— 拿「檔案存在」當檢查會讓
    `T1670b` 一路通過，寫進 DB 才撞外鍵。一律對照真實目錄查正規 id
    （`tripitaka_parallels.canonical_work_id`）。

22. **大正藏行號不唯一。** 同一行可以起頭好幾段 —— 全藏 **65,483 段（6.5%）、
    672 部**如此。行號是段的*引用式*（使用者定調，不改），但不能當鍵：
    拿它 join 對照／詞條，同行的段會互相串；當 DOM anchor 會出現重複 id。
    故每段有兩個欄位：

    | 欄 | 是什麼 | 用途 |
    |---|---|---|
    | `seg` | 大正藏行號 `T02n0099_p0001a06` | 顯示與引用，允許重複 |
    | `uid` | 同行第二段起加 `.2`／`.3` | 對照／詞條／anchor 的**唯一鍵** |

    DB 的 `tripitaka_parallels.seg_uid` 存的是 uid，不是 seg。

23. **🚨 CBETA `<cb:div>` 的 `n` 不是品號，是文件順序的流水號。**
    寶性論 T1611 卷一是本偈（列出十一品），卷二～四是釋論、重出品二／五／六 ——
    那三個節點的 `n` 是 **12／15／16**。`zh_pin_segs` 原本先讀 `n` 再讀標題，
    於是憑空多出品 12／15／16，漢品數從 11 變 14，`--audit` 只報「品數不合」，
    看不出多出來的是幻影品。大乘莊嚴經論 T1604 的「述求品第十二之一／之二」
    同理，`n` 是「之幾」（1、2）不是品號 —— 那更毒：`setdefault(1, …)` 撞到
    既有的品一而**靜默失敗**，品十二根本沒被登記，總數卻剛好還是 24。
    定規：**品號一律讀標題的「第X」，`n` 只作退路。**

24. **GRETIL 的章標題拼寫不一致，regex 寫死尾字會整章漏抓。**
    寶性論的標題有的作 `4. caturthaḥ paricchedaḥ`、有的作
    `2. dvitīya pariccheda`（序數與 pariccheda 都少了尾巴的 ḥ）。
    原 regex 要求 `paricchedaḥ`，第二、三章的標題整個抓不到，內容被默默
    併進第一章 —— 梵本只解出 3 章（實為 5 章），然後被閘擋下，
    看起來像「梵漢分品不同」，其實是自己漏抓。
    **被閘擋下時先確認梵本那一側解對了沒有，再去懷疑梵漢真有差異。**

25. **🚨 建好了不等於看得到 —— 本機 `out/` 與 Drive `_tripitaka/` 是兩份。**
    網站（`server/utils/tripitaka.ts`）只讀 Drive／R2，本機 `C:/tmp/cbeta/out/`
    建出來的東西不 `--sync-drive` 就永遠不會出現在頁面上，而**頁面完全正常**，
    只是少了一整層對照。2026-08-30 一次抓到兩筆：
    - 維摩詰 T0475、金剛經 T0235 的梵文早就建好躺在本機，Drive 沒有 →
      站上只看得到 7 部梵文，SKILL 卻寫 9 部。
    - 十三部已完成的繁中白話 `.zhmod.json` **一個都沒上 Drive** →
      白話欄在全站任何一部經都不會出現。
    收工前一律跑一次「本機 vs Drive 差異」再 `--sync-drive`。
    ⚠ 但 `--sync-drive` 會**無差別複製整個 out/**，包含正在翻譯中的
    `.zhmod.json`（`tripitaka_vernacular` 用 `write_text` 逐批覆寫，非原子），
    複製到一半會拿到截斷的 JSON、讓那部經的 reader 直接壞掉。
    **翻譯還在跑時，只挑已完成的經手動複製，別跑 `--sync-drive`。**

    **🚨 根因是各腳本的產出目錄不一致，2026-08-31 又咬了一次：**

    | 腳本 | 寫到哪 |
    |---|---|
    | `tripitaka_cbeta.py`（正文 JSONL） | **Drive** `_tripitaka/`（`.env` 的 `TRIPITAKA_DIR`） |
    | `tripitaka_sanskrit.py`／`tripitaka_vernacular.py` | **本機** `C:/tmp/cbeta/out` |

26. **🚨「被閘擋下」不等於「梵漢真的分品不同」—— 可能是梵本那側自己解錯了。**

    **被擋下時先驗梵本那一側解出的章數對不對，再去談梵漢差異。**

    另注意：有 `chapter_map` 的條目**不再走品數比對那道閘**，所以「梵本解錯」

    一律要求宣告 `expect_chapters`＝原書尾題條數，對不上就在 `--audit` 擋下。

27. **🚨 X 有 6 部書被切成兩個 XML 檔 —— 逐檔建置會把前半整個蓋掉。**
    印本跨冊時 CBETA 依冊切檔，兩檔同經號、書名尾巴各帶「(第1卷-第44卷)」
    「(第45卷-第80卷)」：華嚴綱要 X08+X09、大乘本生心地觀經淺註 X20+X21、

    五燈嚴統 X80+X81、五燈全書 X81+X82。

    —— 華嚴綱要只剩卷 45–80，少掉前 44 卷，而頁面完全正常。

    否則後半的目錄父子鏈會指到前半的節點上（側欄有東西但層級全錯）。

29. **🚨 收 X 才現形的兩個「靜默丟字」結構**（T／N 一個都沒有，所以先前不會發作）：

31. **X 的部類不能憑記憶寫，也掃不出來。**

### 🚨 DK 的踩坑（與 CBETA 那批並列，程式碼裡逐條標了註解）

    一千多部裡一大半掛著同一個假書名而且看起來很正常。書名只能從正文抽，
    三個取法各自記 `title_source`，不混為一談：

    「…ཞེས་བྱ་བ…རྫོགས་སོ།」，短陀羅尼多屬此類）／**留空 49（4.4%），不填**。
